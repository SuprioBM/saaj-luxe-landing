## PART 1 — PROJECT OVERVIEW

### Purpose
SAAJ is a dark-mode, editorial luxury e-commerce storefront (men's shirts + jewellery: neckchains, rings, bracelets) with a customer account area and an internal "Atelier Desk" admin panel.

### Main features (as they exist today)
| Area | Reality |
| --- | --- |
| Storefront (home, shop, category, product, search) | **Real** — reads the Postgres catalog |
| Cart | **Local only** — `localStorage`, not the `carts`/`cart_items` tables |
| Wishlist | **Local only** — `localStorage`, not the `wishlists` table |
| Checkout + order confirmation | **Local only** — writes to `localStorage`, no payment, no DB row |
| Auth (email/password + Google) | **Real** — Supabase Auth, profiles + roles hydrated |
| Account dashboard | **Shell is real, data is fake** (falls back to local orders) |
| Admin panel | **Shell is real, data is fake, and it is NOT role-gated** |
| Payments | **Not implemented at all** (schema tables exist, zero code) |
| Reviews / coupons / notifications / audit log | **Schema only**, no code |

### User roles
Enum `app_role`: `super_admin`, `admin`, `staff`, `customer`.
`public.has_role()` / `public.is_staff()` wrap security-definer functions in a private `security` schema. `src/lib/auth.ts` collapses these into a frontend `Role = "ADMIN" | "CUSTOMER"`.

### Completion
**~55% of a production platform** (the previous 80% estimate counts UI, not wiring).
- Design system / UI: 95%
- Catalog read path: 90%
- Auth: 80%
- Commerce write path (cart/order/payment/inventory): 5%
- Admin: 25% (UI only)
- Ops (validation, rate limiting, logging, tests): 5%

### Architecture (text diagram)

```
Browser (React 19 + TanStack Router, SSR)
  │
  ├─ supabase-js browser client  ──────────────►  Supabase Postgres (RLS as user/anon)
  │     used by: catalog-live.ts, auth.ts, _authenticated gate
  │
  ├─ localStorage stores (cart, wishlist, orders, recently-viewed)   ← NOT persisted server-side
  │
  └─ src/lib/api.ts  ──fetch(`/api/...`)──►  ✗ NOTHING EXISTS HERE ✗
                                              every call 404s → withFallback() serves
                                              src/lib/api-fallback.ts demo data
Server (Cloudflare Worker via nitro)
  └─ src/server.ts → TanStack Start SSR entry (error-page wrapper only)
        NO createServerFn anywhere.  NO src/routes/api/* anywhere.
```

### Stacks
- **Frontend:** React 19, TanStack Router v1 (file routes), TanStack Start v1, TanStack Query v5, Tailwind CSS v4 (`src/styles.css`, no tailwind.config), shadcn/ui + Radix, lucide-react, sonner, recharts.
- **Backend:** *None written.* The runtime is TanStack Start server functions on Cloudflare Workers. There is no Express, no Prisma, no Node process. Ignore any doc/comment mentioning "Prisma/Express backend" — it is stale intent.
- **Database:** Supabase Postgres, project ref `nvncumadgusdaaabeotf`. No ORM. Schema is raw SQL in `supabase/migrations/*` (source of truth) mirrored in `docs/schema.sql` + `docs/seed_catalog.sql`. Types generated to `src/integrations/supabase/types.ts`.
- **Auth:** Supabase Auth (email/password + Google through the Lovable OAuth broker `@lovable.dev/cloud-auth-js`). Session in `localStorage`, **not** HTTP-only cookies.
- **Third-party:** Supabase, Lovable Cloud auth broker, Google Fonts. That is all.
- **Payments:** none.
- **Storage:** none active. Public bucket creation was blocked, so product imagery is static files in `public/images/*` referenced by absolute path from `product_images.url`.
- **State:** TanStack Query (server data) + `useSyncExternalStore` hand-rolled stores (cart/wishlist/orders/recent/auth) + route search params (shop filters).
- **Deploy:** Lovable-managed; `vite build` → nitro → Cloudflare Worker. `vite.config.ts` points the Start server entry at `src/server.ts`.

## PART 4 — BACKEND FLOW

**There are zero backend endpoints.** Full inventory of server-side code:

| Method | Route | Purpose | Auth | Notes |
| --- | --- | --- | --- | --- |
| GET | `/sitemap.xml` | SEO sitemap | none | `src/routes/sitemap[.]xml.ts`, the only server handler |

```
POST   /api/auth/login           POST /api/auth/logout

POST   /api/admin/uploads
GET    /api/admin/orders         PATCH /api/admin/orders/:id/status

```

Data that *is* reaching Postgres does so straight from the browser via supabase-js under RLS: catalog reads (anon SELECT), `profiles`/`user_roles` reads, `profiles` update.

### Target flow once you build it
```
Component → useServerFn(fn) → createServerFn POST
   → attachSupabaseAuth (client, adds bearer)
   → requireSupabaseAuth (server, validates → context.supabase/userId)
   → zod inputValidator
   → handler: supabase queries under RLS as the user
   → typed JSON back → TanStack Query cache
```
Place them in `src/lib/*.functions.ts` (client-safe path). Webhooks go in `src/routes/api/public/*`. **Do not create Supabase Edge Functions** — the runtime here is the Worker.

## PART 5 — AUTHENTICATION

Files: `src/lib/auth.ts`, `src/routes/auth.tsx`, `src/routes/_authenticated/route.tsx`, `src/routes/__root.tsx` (the single `onAuthStateChange` subscriber), `src/integrations/supabase/{client,auth-attacher,auth-middleware}.ts`, `src/start.ts`, DB trigger fn `public.handle_new_user()`.

- **Signup:** `supabase.auth.signUp({email,password,options.data.name})`. `handle_new_user()` inserts `profiles` + a `customer` row in `user_roles`. Email confirmation is ON, so `data.session` is null and `auth.register` throws "Check your email…" — the UI presents that as an instruction. *There is no `emailRedirectTo`; add one.*
- **Login:** `signInWithPassword` → `applySession()` loads `profiles` + `user_roles` → store emits.
- **Google:** `lovable.auth.signInWithOAuth("google", { redirect_uri: window.location.origin })` — iframe-safe broker; never call `supabase.auth.signInWithOAuth` for Google here.
- **Logout:** `supabase.auth.signOut()` + clear store. **Missing:** `queryClient.cancelQueries()/clear()` and a redirect — cached admin/account data survives a sign-out.
- **Session/JWT:** issued by Supabase (Auth server), stored in **localStorage** by supabase-js, auto-refreshed. *No HTTP-only cookie exists* despite the original spec. Verification happens (a) inside Postgres via RLS `auth.uid()`, (b) in the `_authenticated` gate via `getUser()`. `attachSupabaseAuth` would attach `Authorization: Bearer` to server-fn calls — currently a no-op.
- **Refresh tokens:** handled entirely by supabase-js; no app code.
- **Password reset:** **not implemented.** No `resetPasswordForEmail`, no `/reset-password` route.
- **Email verification:** Supabase default templates; no in-app resend/confirm surface.

## PART 6 — DATABASE

Provider Supabase Postgres · ORM none (raw SQL + supabase-js query builder) · Schema via timestamped migrations.

### Tables (20)
`profiles`, `user_roles`, `addresses`, `categories`, `products`, `product_variants`, `product_images`, `carts`, `cart_items`, `wishlists`, `orders`, `order_items`, `payments`, `coupons`, `coupon_redemptions`, `reviews`, `notifications`, `audit_logs`, `rate_limits`.

Enums: `app_role`, `order_status`(pending→processing→paid→shipped→delivered→cancelled→refunded), `payment_status`, `product_status`, `coupon_kind`, `notification_audience`, `user_status`.

Every table has `id uuid pk default gen_random_uuid()`, `created_at`, and where mutable `updated_at` + `set_updated_at()` trigger. RLS is enabled everywhere with GRANTs; catalog tables allow `anon SELECT`, user-owned tables scope to `auth.uid()`, `rate_limits` is fully locked (service-role only).

### Relationships
```
auth.users
 ├─1:1─ profiles (id → auth.users.id, cascade)
 ├─1:N─ user_roles (unique user_id+role)
 ├─1:N─ addresses (is_default flag, no partial unique index — add one)
 ├─1:N─ carts ──1:N── cart_items ──N:1── product_variants
 ├─1:N─ wishlists ──N:1── products (should be unique(user_id,product_id))
 ├─1:N─ orders ──1:N── order_items   (order_items snapshot name/slug/size/price/image)
 │        └─1:N─ payments (stripe_session_id, stripe_payment_intent_id)
 │        └─N:1─ coupons ──1:N── coupon_redemptions
 ├─1:N─ reviews ──N:1── products (verified flag, optional order_id)
 ├─1:N─ notifications (audience user|admin)
 └─1:N─ audit_logs (actor_id)

categories ─self─ parent_id (category → subcategory)
categories ─1:N─ products (category_id, subcategory_id)
products ─1:N─ product_variants (size, stock, reserved)
products ─1:N─ product_images (position, is_primary)
```
`orders.user_id` is nullable → guest checkout is schema-supported. `order_items` denormalises product data so history survives catalog edits. `product_variants.reserved` exists for a reserve-on-checkout / commit-on-paid flow that is not written yet.

**Seeded:** 4 categories, 9 products, gallery images, per-size stock. Everything else is empty.

## PART 7 — E-COMMERCE FLOWS (current vs required)

**Products** — Read: `useProducts()` → supabase-js → `products + categories + product_images + product_variants` under anon RLS. ✅
Create/edit/delete/stock: `ProductForm` → `queries.ts` mutation → `api.admin.*` → 404 → `api-fallback` in-memory array. Changes vanish on reload. ❌
Image upload: `api.admin.uploadImage` posts multipart to a non-existent route; fallback returns a data URL. ❌

**Wishlist** — `wishlistStore` slug array in localStorage. Not per-user, not synced, lost on device change. ❌

**Cart** — `cartStore` lines `{slug,size,qty}` in localStorage; stock validated against **static** `catalog.ts`; prices read from the static file. Guest and signed-in are identical; no merge on login. ❌

**Checkout** —
```
/checkout (details → payment → review)
  → validate in component
  → ordersStore.place()  → localStorage
  → navigate /order/$id
```
No DB row, no payment, no stock decrement, no email, no failure path. ❌

**Target flow to build**
```
Cart page → createCheckout(serverFn)
  → validate cart against product_variants (stock - reserved)
  → apply coupon (validate code/window/min/limit)
  → INSERT orders(status=pending) + order_items snapshot
  → increment product_variants.reserved
  → Stripe Checkout Session (metadata.order_id) → redirect
Stripe → POST /api/routes/api/public/webhooks/stripe
  → verify signature (raw body, timing-safe)
  → checkout.session.completed: payments row succeeded,
    orders.status=paid, stock -= qty, reserved -= qty,
    notifications(user+admin), audit_logs
  → payment_failed / expired: release reserved, orders.status=cancelled
Browser returns to /order/$reference → reads DB (poll until paid)
```
All stock mutations must be a single Postgres function called via RPC so they are atomic.

## PART 9 — ADMIN SYSTEM

Routes `/admin`, `/admin/products`, `/admin/orders`, `/admin/customers` (`src/routes/_authenticated/admin.*.tsx`), shell `AdminShell.tsx`.

**🔴 Critical:** the only guard is the `_authenticated` layout — *any signed-in customer can open `/admin`*. `AdminShell` reads `useAuth()` but never checks `user.role`. There is no admin middleware and no server-side authorisation, because there is no server. Today the exposure is limited to mock data; the moment admin APIs are real this is a full privilege-escalation hole.

Fix: add `src/routes/_authenticated/_admin/route.tsx` with `beforeLoad` calling `has_role(uid,'admin')` and redirecting otherwise, move the admin routes under it, **and** re-check the role inside every admin server function (`context.supabase.rpc('has_role', …)` — never trust the client).

**Admin credentials are not stored in the codebase.** No seeded admin user, no default email, no default password. Every signup gets `customer` via `handle_new_user()`.

To create one: sign up normally through `/auth`, then run a migration/SQL insert:
```sql
insert into public.user_roles (user_id, role)
select id, 'admin' from auth.users where email = 'you@example.com'
on conflict (user_id, role) do nothing;
```
(`user_roles` denies client-side INSERT by policy, which is correct — grants must come from a migration or a privileged server fn.)

## "IF I TAKE OVER THIS PROJECT TODAY" — EXACT PLAN

**Day 0 — set up (2h)**
`bun install`; `bun run dev`; confirm `/`, `/shop`, `/product/...` render from the DB. Link the Supabase CLI, `db pull`, regenerate types. Sign up an account, grant yourself `admin` with the SQL in Part 9.

**Day 1 — close the security hole (4h)**
Create `src/routes/_authenticated/_admin/route.tsx` with a `beforeLoad` that calls `supabase.rpc('has_role', {_user_id, _role:'admin'})` and redirects non-admins. Move `admin.*.tsx` under it and fix the route IDs. Add `errorComponent`/`notFoundComponent` to every route with a loader. Fix sign-out hygiene.

**Day 2 — the server layer (8h)**
Create `src/lib/products.functions.ts` as the template: `createServerFn({method:'POST'}).middleware([requireSupabaseAuth]).inputValidator(zod).handler(...)`. Keep those files thin — imports and exported fns only, helpers in a sibling module (the splitter deletes runtime siblings otherwise). Verify `attachSupabaseAuth` is delivering the bearer.

**Days 3–4 — admin against the DB (12h)**
Product create/update/delete/stock as admin server fns that re-check the role server-side. Rewrite `queries.ts` to `useServerFn` and drop `withFallback`. Storage bucket (your own Supabase project) or keep `public/images` + a signed upload fn. Delete `api-fallback.ts`.

**Days 5–6 — cart & wishlist (12h)**
`carts`/`cart_items` server fns; price from the DB; guest cart in localStorage merged on `SIGNED_IN`. Wishlist to the `wishlists` table with a unique constraint. Cart badge and stock checks read live variant stock.

**Days 7–8 — orders (14h)**
A Postgres function `place_order(...)` doing everything in one transaction: validate stock, snapshot `order_items`, bump `reserved`, return the order. Checkout calls it, then account/admin orders read the DB. Kill `src/lib/orders.ts`.

**Days 9–11 — Stripe (16h)**
Add secrets + the SDK. `createCheckoutSession` fn with `metadata.order_id`. `src/routes/api/public/webhooks/stripe.ts`: raw body, timing-safe HMAC, idempotent on `stripe_session_id`, then paid → decrement stock, release `reserved`, write `payments` + `notifications` + `audit_logs`. Test with the Stripe CLI against the `-dev.lovable.app` URL. Handle expiry/failure by releasing reserve.

**Day 12 — auth completion (5h)** password reset flow + `/reset-password`, `emailRedirectTo` on signup, resend-verification UI, addresses CRUD.

**Days 13–14 — commerce depth (12h)** reviews (verified-buyer), coupons at checkout, notifications, admin order-status transitions with audit rows.

**Day 15 — hardening (8h)** zod everywhere, `rate_limits`-backed limiter, structured logging + monitoring, server-side search/pagination, dependency cleanup, lazy recharts, run the security linter, Lighthouse.

**Day 16 — tests & launch (8h)** vitest on pricing/stock/coupon logic, Playwright E2E for browse→cart→checkout→webhook→order, production build + preview, then publish.
